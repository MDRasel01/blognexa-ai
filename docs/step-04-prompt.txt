# 1. EXECUTIVE OBJECTIVE

Implement a secure, reliable and tenant-isolated communication architecture between BlogNexa AI WordPress installations and the central cloud backend.

The implementation must establish:

- Unique website identity.
- Secure site enrollment.
- Backend authentication.
- Request integrity verification.
- Replay attack protection.
- Credential encryption and rotation.
- Tenant isolation.
- Resource-level authorization.
- API rate limiting.
- Audit logging.
- Secure connection lifecycle.
- SSRF protection.
- Failure recovery.
- Security testing.

The system must support multiple WordPress websites connected to the same BlogNexa AI backend without exposing one website's private data to another.

## 1.1 Non-negotiable security principles

1. Never trust client-supplied tenant IDs.
2. Never expose backend master credentials to WordPress Admin JavaScript.
3. Never place provider API secrets in browser code.
4. Never use a nonce as a substitute for authentication.
5. Never treat HMAC authentication as user authorization.
6. Never allow an authenticated site to access another site's data.
7. Never accept unsigned or expired protected requests.
8. Never log authentication secrets.
9. Never allow arbitrary internal network access through the crawler.
10. Never claim security validation passed without executing the relevant tests.

# 3. SECURITY THREAT MODEL

Before implementation, document the threats the architecture must defend against.

## 3.1 Threat Categories

### A. Credential Theft

Potential attacks:

- Database backup theft.
- WordPress configuration exposure.
- Malicious plugin access.
- Server compromise.
- Credential leakage in logs.
- Browser-side secret exposure.

Required defenses:

- Encrypt stored site credentials.
- Keep encryption keys outside the WordPress database.
- Use server-side credential access only.
- Redact logs.
- Support credential rotation and revocation.

### B. Unauthorized API Access

Potential attacks:

- Requests without credentials.
- Forged site identifiers.
- Stolen credentials.
- Unauthorized API operations.

Required defenses:

- Authentication middleware.
- Request signature validation.
- Timestamp validation.
- Replay protection.
- Per-operation authorization.
- Resource ownership checks.

### C. Cross-Tenant Data Access

Potential attacks:

- Manipulating tenant identifiers.
- Guessing document IDs.
- Accessing another site's job.
- Retrieving another site's knowledge chunks.
- Modifying another site's publishing records.

Required defenses:

- Server-derived tenant identity.
- Tenant-scoped database queries.
- Ownership checks.
- PostgreSQL row-level security where appropriate.
- Automated cross-tenant tests.

### D. SSRF

Potential attacks:

- Accessing localhost.
- Accessing private IP ranges.
- Accessing cloud metadata endpoints.
- DNS rebinding.
- Redirecting an allowed URL to an internal IP.

Required defenses:

- URL validation.
- DNS resolution validation.
- Private/reserved IP blocking.
- Redirect revalidation.
- Egress restrictions.
- Response size limits.

### E. Replay and Abuse

Potential attacks:

- Reusing a valid signed request.
- Repeated expensive AI requests.
- API flooding.
- Brute-force enrollment attempts.

Required defenses:

- Request timestamp.
- Unique nonce.
- Redis replay cache.
- Rate limiting.
- Idempotency.
- Abuse monitoring.

# 4. SITE IDENTITY ARCHITECTURE

Every WordPress installation must have a unique identity.

Do not identify a site only by its domain name.

Domains can change, installations can move, and multiple environments can use similar URLs.

## 4.1 Site Identity Fields

Recommended identity:

```
tenant_id
site_id
site_instance_id
environment
registered_domain
registration_status
created_at
last_seen_at
```

Definitions:

- `tenant_id`: Account or organization ownership.
- `site_id`: Registered website record.
- `site_instance_id`: Unique WordPress installation identity.
- `environment`: Production, staging or development.
- `registered_domain`: Verified canonical site address.

Use UUIDs for internal identifiers.

The backend must create and own the authoritative tenant and site records.

## 4.2 Site Identity Generation

Generate a cryptographically random installation identifier during plugin initialization or activation.

Example:

```
$site_instance_id = wp_generate_uuid4();
```

Persist it using a protected WordPress option.

Requirements:

- Generate once.
- Do not regenerate during normal plugin updates.
- Do not trust a user-submitted value.
- Do not use it as a secret.
- Provide an explicit reset/re-registration process.

A copied staging database may duplicate this identifier. Detect duplicate active installations and require a deliberate staging registration workflow.

# 5. SECURE SITE ENROLLMENT

The initial connection process must not expose permanent credentials through URLs or browser storage.

## 5.1 Recommended Enrollment Flow

Use a short-lived, single-use enrollment code.

```
User Opens BlogNexa Settings
          |
          v
Clicks Connect Website
          |
          v
WordPress Plugin Requests Enrollment
          |
          v
Backend Creates Temporary Enrollment Session
          |
          v
User Completes Account Authorization
          |
          v
Backend Issues Single-Use Enrollment Code
          |
          v
WordPress Plugin Exchanges Code
          |
          v
Backend Verifies Enrollment
          |
          v
Backend Creates Site Registration
          |
          v
Backend Issues Site Credentials
          |
          v
Plugin Encrypts and Stores Credentials
          |
          v
Authenticated Connection Established
```

## 5.2 Enrollment Code Requirements

The enrollment code must:

- Be generated using a cryptographically secure random generator.
- Have a short expiration time.
- Be single-use.
- Be bound to the intended enrollment session.
- Be bound to the authorized tenant.
- Be invalidated after successful exchange.
- Be stored hashed on the backend.
- Never appear in application logs.
- Never be sent to an arbitrary redirect URL.

Suggested initial expiration: 5 minutes.

The final value must be configurable according to security testing.

## 5.3 Enrollment Endpoint Contract

Example:

`POST /v1/enrollment/sessions`

Purpose:

Create an enrollment session.

The backend must verify the account's authorization before issuing a usable enrollment session.

Example response:

```
{
  "enrollment_id": "uuid",
  "authorization_url": "https://app.example.com/authorize/...",
  "expires_at": "2026-11-09T16:00:00Z"
}
```

The authorization URL must be generated by the backend and use an approved destination.

After authorization:

`POST /v1/enrollment/exchange`

Example request:

```
{
  "enrollment_code": "single-use-code",
  "site_instance_id": "uuid",
  "site_url": "https://example.com",
  "environment": "production"
}
```

The backend must verify the enrollment code and authorization context.

Example response:

```
{
  "site_id": "uuid",
  "tenant_id": "uuid",
  "credential_id": "uuid",
  "key_version": 1,
  "site_secret": "one-time-secret",
  "status": "connected"
}
```

This is a conceptual contract. Final field names and response schemas must be reviewed against the actual implementation.

The secret is returned once over HTTPS and must never be returned by normal status endpoints.

## 5.4 Enrollment Abuse Protection

Implement:

- Rate limits.
- Expiration.
- Single-use verification.
- Attempt counters.
- Account-level authorization.
- Security event logging.
- Enrollment revocation.

# 6. CREDENTIAL STORAGE AND ENCRYPTION

Credential security is critical because a stolen site credential could allow an attacker to impersonate a registered website.

## 6.1 WordPress Storage

The WordPress Plugin may store:

- Site ID.
- Tenant ID.
- Credential ID.
- Key version.
- Encrypted site secret.
- Connection status.
- Last successful connection.

Do not store the secret as plaintext in the WordPress options table.

## 6.2 Encryption Strategy

Use authenticated encryption such as libsodium secretbox or another reviewed authenticated encryption mechanism.

The encryption key must not be stored alongside the encrypted database value.

Recommended deployment configuration:

```
BLOGNEXA_CREDENTIAL_ENCRYPTION_KEY
```

Place the encryption key in protected server configuration, preferably `wp-config.php` or an equivalent secret-management mechanism.

Requirements:

- Validate key length and format.
- Fail closed when the encryption key is unavailable.
- Never silently fall back to plaintext.
- Use a unique random nonce for each encryption operation.
- Store ciphertext and nonce together in a versioned format.
- Support key rotation.
- Do not include encryption keys in diagnostic reports.

Example storage structure:

```
{
  "version": 1,
  "algorithm": "secretbox",
  "nonce": "base64-value",
  "ciphertext": "base64-value"
}
```

This is a conceptual storage format, not a requirement to use JSON in the database.

## 6.3 Shared Hosting Considerations

On shared hosting, the encryption key in `wp-config.php` is still accessible to PHP and may be exposed if the server itself is compromised.

Encryption protects database exports and backups from some forms of offline credential theft. It does not protect credentials from a fully compromised WordPress server.

Document this limitation.

## 6.4 Backend Secret Storage

The backend must:

- Encrypt site secrets at rest.
- Use a managed KMS or equivalent key-management service where available.
- Restrict access to credential-decryption operations.
- Separate application secrets from tenant data.
- Record key versions.
- Support credential revocation.
- Avoid exposing secrets in database query logs.

Never use a hardcoded production master encryption key in source code.

# 7. AUTHENTICATED API REQUESTS

Use HTTPS for all communication.

For site-to-backend authentication, implement HMAC-SHA256 request signing with a per-site secret.

HMAC is an authentication and integrity mechanism. It is not encryption. HTTPS remains mandatory.

## 7.1 Request Headers

Recommended headers:

```
Authorization: BNX-HMAC credential_id="uuid", signature="hex"
X-BNX-Timestamp: 1794240000
X-BNX-Nonce: random-unique-value
X-BNX-Key-Version: 1
X-BNX-Request-ID: uuid
X-BNX-Content-SHA256: hex-digest
Content-Type: application/json
```

The exact authorization header syntax must be standardized and implemented identically in PHP and Python.

## 7.2 Canonical Request

Both systems must sign the same canonical representation.

Recommended structure:

```
HTTP_METHOD
CANONICAL_PATH
CANONICAL_QUERY
TIMESTAMP
NONCE
KEY_VERSION
REQUEST_ID
BODY_SHA256
```

Example:

```
POST
/v1/site/status
environment=production
1794240000
unique-nonce
1
request-uuid
body-sha256
```

Rules:

- Normalize the HTTP method.
- Use the exact canonical route path.
- Sort query parameters deterministically.
- Define percent-encoding rules.
- Define treatment of empty query values.
- Hash the exact transmitted request body bytes.
- Avoid signing a reserialized JSON body.
- Reject malformed canonical requests.

Both PHP and Python implementations must have shared test vectors.

## 7.3 Signature Generation

Conceptual PHP example:

```
$body_hash = hash('sha256', $body);

$canonical = implode("\n", [
    strtoupper($method),
    $path,
    $canonical_query,
    (string) $timestamp,
    $nonce,
    (string) $key_version,
    $request_id,
    $body_hash,
]);

$signature = hash_hmac(
    'sha256',
    $canonical,
    $site_secret
);
```

The production implementation must use the exact canonicalization specification and ensure `$body` is the same byte sequence transmitted.

## 7.4 Backend Verification

FastAPI middleware or a dedicated authentication dependency must:

1. Parse authentication headers.
2. Validate required fields.
3. Locate the credential record.
4. Check credential status.
5. Check key version.
6. Validate timestamp.
7. Validate nonce format.
8. Calculate the request body hash.
9. Reconstruct the canonical request.
10. Calculate the expected signature.
11. Compare signatures using a constant-time comparison function.
12. Atomically register the nonce.
13. Resolve the site and tenant from the authenticated credential.
14. Attach the authenticated principal to the request context.

Reject invalid requests before executing protected business logic.

## 7.5 Timestamp Window

Suggested initial tolerance:

5 minutes.

The value must be configurable and tested against realistic hosting clock drift.

Servers must use synchronized time.

Do not rely on timestamps alone for replay protection.

## 7.6 Constant-Time Comparison

Use an appropriate constant-time comparison function.

Python example:

```
import hmac

is_valid = hmac.compare_digest(
    expected_signature,
    received_signature
)
```

Never use ordinary string equality as the security comparison for the signature.

# 8. REPLAY ATTACK PROTECTION

A valid request must not be reusable indefinitely.

## 8.1 Redis Nonce Storage

Use a Redis key similar to:

```
bnx:replay:{credential_id}:{nonce}
```

Store it with an atomic operation equivalent to:

```
SET key value NX EX ttl
```

If the key already exists, reject the request.

The nonce registration must be atomic.

## 8.2 Replay Rules

Reject requests when:

- Timestamp is outside the allowed window.
- Nonce already exists.
- Nonce format is invalid.
- Signature does not match.
- Credential is revoked.
- Key version is unsupported.

If Redis is unavailable, protected write operations must fail closed rather than silently disabling replay protection.

A documented availability strategy may be introduced later, but it must not bypass replay validation.

## 8.3 Idempotency

Replay protection and idempotency solve different problems.

- Replay protection blocks reuse of the same signed request.
- Idempotency prevents duplicate business operations when legitimate retries occur.

For important write operations, support:

`Idempotency-Key`

Store:

- Key.
- Credential ID.
- Route.
- Request body hash.
- Processing status.
- Original response reference.
- Expiration.

Reusing the same key with a different request body must be rejected.

Publishing, job creation and other non-repeatable operations require explicit idempotency behavior.

# 9. TENANT ISOLATION

This is one of the most important requirements of BlogNexa AI.

A single backend may serve hundreds or thousands of WordPress websites.

Each site's data must remain isolated.

## 9.1 Tenant Resolution

Never accept `tenant_id` as an authoritative value from:

- React state.
- Request body.
- Query parameters.
- Custom headers.
- URL path supplied by the user.

Resolve tenant identity from the authenticated credential record.

Example:

```
Authenticated Credential
          |
          v
Registered Site
          |
          v
Tenant Membership
          |
          v
Trusted Request Context
```

The request context should contain:

```
authenticated_credential_id
authenticated_site_id
authenticated_tenant_id
authenticated_permissions
```

## 9.2 Database Schema Requirements

Every tenant-owned table must include the appropriate ownership fields.

Examples:

```
tenants
sites
site_credentials
knowledge_documents
knowledge_chunks
research_jobs
articles
publications
integrations
audit_events
usage_records
```

Recommended ownership fields:

```
tenant_id
site_id
created_at
updated_at
```

Not every table requires both `tenant_id` and `site_id`, but the ownership model must be explicit.

## 9.3 Tenant-Scoped Query Rules

Every database operation must be scoped to the authenticated tenant and, where required, the authenticated site.

Conceptual query:

```
SELECT *
FROM knowledge_documents
WHERE tenant_id = :authenticated_tenant_id
  AND site_id = :authenticated_site_id;
```

Never trust an unverified identifier supplied by the frontend.

## 9.4 PostgreSQL Row-Level Security

Use PostgreSQL Row-Level Security where it materially improves defense in depth.

Requirements:

- Define policies for tenant-owned tables.
- Set tenant context safely within the transaction.
- Use transaction-local settings where appropriate.
- Ensure connection pooling cannot leak tenant context.
- Avoid application roles that bypass RLS.
- Test all access paths.

RLS must complement—not replace—application-level authorization.

## 9.5 RAG Isolation

The knowledge retrieval layer must filter by tenant and site before returning candidate chunks.

Required retrieval scope:

```
tenant_id = authenticated tenant
site_id = authenticated site
document_status = eligible
```

Never perform unrestricted vector retrieval and then filter results only in the frontend.

Cross-tenant RAG leakage is a critical security failure.

## 9.6 Cross-Tenant Test

Create at least two test tenants:

```
Tenant A
  Site A1
  Site A2

Tenant B
  Site B1
```

Verify:

- A1 cannot access B1 documents.
- A2 cannot access B1 jobs.
- B1 cannot access A1 publications.
- Tenant A cannot retrieve Tenant B embeddings.
- Forged tenant IDs do not change access.
- Revoked credentials cannot access any protected tenant resource.

# 10. AUTHORIZATION ARCHITECTURE

Authentication answers:

"Who is making this request?"

Authorization answers:

"What is this authenticated principal allowed to do?"

These must remain separate.

## 10.1 Backend Permission Model

Create explicit permission scopes.

Example:

```
site:read
site:manage
knowledge:read
knowledge:write
research:read
research:write
content:read
content:write
publishing:approve
publishing:execute
integrations:manage
analytics:read
billing:read
```

The actual permissions must be approved against the product's business rules.

## 10.2 Site-Level Permissions

The backend must determine whether a registered site is allowed to perform a requested operation.

For example:

- A site may read its own status.
- A site may submit an approved scan job.
- A site may retrieve its own research results.
- A site may publish only through the approved publishing policy.

A WordPress user being an Administrator does not automatically grant access to every backend tenant operation.

## 10.3 WordPress Capability Enforcement

Continue using the Step 01 capability architecture.

Examples:

```
current_user_can('blognexa_manage_settings');
current_user_can('blognexa_scan_website');
current_user_can('blognexa_publish_blog');
```

Every protected WordPress REST route must:

- Define a permission callback.
- Check the relevant capability.
- Validate resource ownership.
- Validate request parameters.
- Return a consistent error response.

A REST nonce is a CSRF defense for authenticated cookie-based requests. It is not a replacement for WordPress capability checks or site-to-backend authentication.

# 11. CREDENTIAL ROTATION AND REVOCATION

Credentials must have a complete lifecycle.

## 11.1 Rotation Strategy

Use a staged rotation process.

```
Current Key Version: 1
          |
          v
Backend Creates Key Version 2
          |
          v
New Credential Delivered Securely
          |
          v
Plugin Stores New Credential
          |
          v
Plugin Verifies New Credential
          |
          v
Backend Marks Version 2 Active
          |
          v
Old Version 1 Revoked
```

The backend may temporarily accept both versions during a controlled transition.

Do not accept old keys indefinitely.

## 11.2 Rotation Requirements

- Every key has a version.
- Every credential has a status.
- Every rotation has an audit record.
- Rotation is authenticated.
- New credentials are verified before old credentials are revoked.
- Failed rotation has a recovery procedure.
- Compromised credentials can be revoked immediately.

## 11.3 Revocation

Support:

- Manual disconnect.
- Administrator-initiated revocation.
- Backend-initiated revocation.
- Credential compromise response.
- Site deletion.
- Account suspension.

A revoked credential must stop working immediately or within a documented, tightly bounded cache invalidation window.

# 12. RATE LIMITING AND ABUSE PROTECTION

Rate limits must apply at multiple levels.

## 12.1 Rate-Limit Dimensions

- IP address.
- Credential ID.
- Site ID.
- Tenant ID.
- Endpoint.
- Operation type.
- Expensive AI task.
- Enrollment session.

## 12.2 Different Operation Classes

Example:

| Operation          | Risk        | Suggested Control                    |
| ------------------ | ----------- | ------------------------------------ |
| Read site status   | Low         | Moderate rate limit                  |
| Read settings      | Low         | Moderate rate limit                  |
| Website scan       | High cost   | Job quota                            |
| SEO research       | High cost   | Usage quota                          |
| Article generation | High cost   | Token and job limits                 |
| Image generation   | High cost   | Provider quota                       |
| Publishing         | High impact | Strict authorization and idempotency |

Do not apply a single global rate limit to all operations.

## 12.3 Response Behavior

Return a consistent response:

```
{
  "code": "RATE_LIMITED",
  "message": "Request limit exceeded.",
  "retry_after": 30
}
```

Include an appropriate HTTP status and `Retry-After` header.

Never reveal internal rate-limit implementation details.

## 12.4 Quotas

The future SaaS billing system will need:

- Tenant usage limits.
- Per-site usage.
- Per-operation quotas.
- AI token consumption.
- Image generation usage.
- Research job limits.

Step 04 must establish the enforcement foundation without implementing an unapproved billing system.

# 13. SSRF PROTECTION AND CRAWLER SECURITY

BlogNexa AI reads external website content. This introduces a serious SSRF risk.

The crawler must never become a proxy into internal infrastructure.

## 13.1 Blocked Destinations

Reject requests targeting:

- `localhost`.
- Loopback addresses.
- Private IPv4 ranges.
- Private IPv6 ranges.
- Link-local addresses.
- Multicast and reserved ranges.
- Cloud metadata endpoints.
- Internal infrastructure hostnames.
- Unapproved protocols.

Also block IPv4-mapped IPv6 forms and alternative IP representations.

## 13.2 DNS Rebinding Defense

A hostname may resolve to a public IP during validation and an internal IP during connection.

Required controls:

1. Resolve the hostname.
2. Validate all resolved IP addresses.
3. Reject prohibited destinations.
4. Connect only to an approved resolved destination.
5. Ensure the HTTP client cannot silently re-resolve to an unapproved destination.
6. Validate every redirect target again.

Implement the network controls in the backend infrastructure where possible.

## 13.3 Redirect Rules

- Set a strict redirect limit.
- Revalidate every redirect.
- Block redirects to prohibited networks.
- Do not forward sensitive authorization headers to a different host.
- Reject unsupported protocols.

## 13.4 Response Limits

Apply:

- Connection timeout.
- Read timeout.
- Maximum response size.
- Maximum decompressed size.
- Maximum redirects.
- Allowed content types.
- Maximum processing time.
- Concurrency limits.

Protect against oversized compressed responses and decompression bombs.

## 13.5 Content Parsing

- Do not execute downloaded JavaScript.
- Do not execute downloaded PHP.
- Do not treat website content as trusted instructions.
- Keep retrieved page content separate from system instructions.
- Defend AI/RAG workflows against prompt injection.
- Preserve source attribution.

## 13.6 Network-Level Defense

Where possible, run crawling workers with restricted outbound network access.

Application-level URL checks are necessary but not sufficient by themselves.

```
      |

      |
      v

```

## 17.1 State Definitions

| State              | Meaning                            |
| ------------------ | ---------------------------------- |
| Disconnected       | No active site credentials         |
| Enrollment Pending | User authorization is pending      |
| Authenticating     | Credentials are being verified     |
| Connected          | Authenticated connection verified  |
| Degraded           | Temporary communication problem    |
| Retrying           | Controlled recovery is in progress |
| Revoked            | Backend has revoked the credential |

Do not represent a site as connected simply because credentials exist locally.
