# 1. EXECUTIVE OBJECTIVE

The objective of Step 03 is to build a complete, production-ready administrative interface for BlogNexa AI inside WordPress Admin.

The interface must provide a consistent experience across all product modules.

The UI must be:

- Modular.
- Responsive.
- Accessible.
- Permission-aware.
- API-driven.
- Maintainable.
- Performance-conscious.
- Compatible with WordPress Admin.
- Consistent with the approved product architecture.

The interface must not contain duplicated business logic or direct AI-provider communication.

## 1.1 Primary Product Experience

The user opens WordPress Admin and sees:

```
WordPress Admin
      |
      v
BlogNexa AI
      |
      v
BlogNexa AI Admin Application
      |
      +-- Overview
      +-- Website Intelligence
      +-- Knowledge Base
      +-- Content Strategy
      +-- SEO Research
      +-- Blog Studio
      +-- Image Studio
      +-- Publishing & Scheduling
      +-- Performance Analytics
      +-- Integrations
      +-- Settings
```

All these modules must remain within the WordPress plugin interface.

## 1.2 What Step 03 Must Deliver

At the end of this phase:

1. The React application must mount correctly.
2. Sidebar navigation must work.
3. Every module must have its own route and page component.
4. Page permissions must be respected.
5. The centralized API client must work.
6. Loading, error, empty and unavailable states must be implemented.
7. Settings must integrate with the existing REST API.
8. Dashboard information must come from real backend responses where available.
9. Responsive behavior must be verified.
10. UI and integration tests must pass.

# 2. DESIGN AND ENGINEERING PRINCIPLES

## 2.1 Design Philosophy

BlogNexa AI should feel like a professional content operations platform.

Design priorities:

1. Information clarity.
2. Operational visibility.
3. Minimal unnecessary complexity.
4. Fast navigation.
5. Consistent interaction patterns.
6. Accessible controls.
7. Clear separation of AI-generated and verified information.

Avoid designing the dashboard as a decorative marketing website.

## 2.2 Design System Principles

Use a controlled design system.

Every component must use shared design tokens rather than arbitrary individual values.

Define:

- Color tokens.
- Typography scale.
- Spacing scale.
- Border radius.
- Shadows.
- Z-index levels.
- Layout widths.
- Breakpoints.
- Interaction states.
- Focus states.
- Status colors.

## 2.3 Visual Direction

Proposed visual direction:

- Clean, modern SaaS-style admin interface.
- Neutral light background.
- White or neutral content surfaces.
- Dark text.
- Subtle borders.
- Restrained accent color.
- Clear typography hierarchy.
- Compact operational data tables.
- Consistent icons.

The final accent palette must be approved and stored in the design tokens.

Do not scatter hardcoded colors throughout the components.

# 4. FRONTEND TECHNOLOGY ARCHITECTURE

## 4.1 Required Technology

- React.
- TypeScript.
- WordPress Components.
- WordPress Element where appropriate.
- WordPress REST API.
- npm.
- Vite or the approved WordPress-compatible build pipeline.
- ESLint.
- TypeScript compiler.

Use the WordPress-provided packages and dependencies appropriately.

Do not bundle an unnecessary second copy of React when the WordPress environment already provides the required runtime.

The final build strategy must be compatible with the approved WordPress and PHP versions.

## 4.2 Application Architecture

Separate the application into these layers:

```
React Admin Application
        |
        v
Presentation Layer
        |
        v
Page Components
        |
        v
Feature Components
        |
        v
Application Services
        |
        v
API Client
        |
        v
WordPress REST API
        |
        v
Plugin Controllers
```

Responsibilities:

| Layer          | Responsibility                        |
| -------------- | ------------------------------------- |
| Presentation   | Visual layout and styling             |
| Pages          | Page-level composition                |
| Features       | Module-specific components            |
| Services       | Business-oriented frontend operations |
| API Client     | HTTP communication                    |
| WordPress REST | Authorization and server operations   |

Do not place REST requests directly inside every button component.

Do not let visual components independently construct API URLs.

# 6. APPLICATION BOOTSTRAP

Files:

```
resources/js/admin/index.tsx
resources/js/admin/App.tsx
```

## 6.1 Bootstrap Responsibilities

- Locate the React root element.
- Read the server-provided configuration.
- Validate required configuration.
- Initialize the application.
- Register global error handling.
- Initialize navigation.
- Mount the React application.
- Avoid duplicate mounting.

## 6.2 Server Configuration

WordPress may provide:

- REST API root.
- REST nonce.
- Current user's permitted capabilities.
- Plugin version.
- Current route.
- Site locale.
- Plugin configuration.

This information must be provided through a safe server-side mechanism.

Never provide:

- AI API keys.
- Backend signing keys.
- Raw authentication secrets.
- Private infrastructure credentials.

The frontend must not assume that a capability value supplied during page rendering remains authoritative forever. The backend must check permissions again on every protected operation.

# 9. GLOBAL APPLICATION STATES

All modules must follow consistent state handling.

## 9.1 Loading State

Use a skeleton or spinner based on the expected loading duration.

Do not display fabricated metrics while data is loading.

## 9.2 Empty State

An empty state must explain:

- What the module does.
- Why there is no data yet.
- What action the user can take next.

## 9.3 Error State

An error must explain:

- What operation failed.
- Whether the issue is recoverable.
- What the user can do.
- Whether retry is safe.

Never show raw stack traces to users.

## 9.4 Permission State

If the current user lacks permission:

- Hide or disable the relevant action according to UX policy.
- Explain that the user does not have the required permission.
- Do not leak protected data.
- Let the REST API enforce the final decision.

## 9.5 Unconfigured State

For example, if the backend is not connected:

Display a clear connection requirement instead of showing fake successful data.

## 9.6 Offline or Backend Unavailable State

The application must distinguish:

- WordPress REST failure.
- Backend connection failure.
- AI provider unavailable.
- Temporary network interruption.
- Invalid configuration.

A failed AI provider must not make the entire WordPress Admin application unusable.

# 21. CENTRALIZED API CLIENT

File:

`resources/js/services/api-client.ts`

All frontend requests must use one API client.

Responsibilities:

- Read the WordPress REST API base URL.
- Read the current REST nonce.
- Send requests.
- Normalize responses.
- Normalize errors.
- Handle authentication failures.
- Handle network failures.
- Support cancellation.
- Support pagination.
- Prevent accidental duplicate submissions where appropriate.

## 21.1 Request Rules

- Use same-site WordPress REST routes.
- Send the appropriate nonce header for authenticated cookie-based REST requests.
- Do not store credentials in local storage.
- Do not hardcode production URLs.
- Do not expose backend secrets.
- Use bounded request timeouts where appropriate.
- Validate response structure before consuming it.

## 21.2 Error Model

Standard frontend errors:

```
VALIDATION_ERROR
AUTHENTICATION_ERROR
PERMISSION_ERROR
NOT_FOUND
NETWORK_ERROR
BACKEND_UNAVAILABLE
CONFIGURATION_ERROR
SERVER_ERROR
UNKNOWN_ERROR
```

The UI should map server errors into understandable messages.

Do not expose raw internal exceptions.

# 22. STATE MANAGEMENT

Use the simplest state architecture that fits the application.

Recommended:

- Local component state for simple interactions.
- Shared context for global app configuration.
- A dedicated server-state library only if the application complexity justifies it.
- URL state for navigation and shareable filters where appropriate.

Avoid introducing multiple competing state libraries.

## 22.1 Server State vs UI State

Server state includes:

- Website scan status.
- Settings.
- Jobs.
- Knowledge documents.
- Articles.
- Publication records.

UI state includes:

- Open sidebar.
- Selected tab.
- Modal visibility.
- Temporary form values.
- Table selection.

Do not duplicate authoritative server data in multiple unrelated stores.

## 22.2 Cache Rules

- Define cache freshness.
- Invalidate after successful mutations.
- Avoid caching secrets.
- Avoid displaying stale status as current.
- Provide explicit refresh behavior.
- Handle backend reconnection.

8. Never expose internal error details.
9. Avoid sensitive browser storage.

Every important action must be protected by server-side capability and resource ownership checks.
